# Qwen3-0.6B W8A8 on SA8797P — Design

*Date: 2026-08-12 · Status: approved · Target: Qualcomm SA8797P (Hexagon v81
HTP, Android GVM), QAIRT 2.48.40.260702, libGenie 1.19*

## 1. Goal

Build a **W8A8** Qwen3-0.6B Genie bundle — int8 weights (already the case) plus
**int8 activations including the KV cache** — and publish it to Hugging Face.

This is a **re-attempt at a documented dead end**, not new ground.
`SA8797P_Deployment_Status_Summary.md:168` records W8A8 attempts v15–v18 all
producing garbage output, attributed to per-tensor UINT8 asymmetric activation
quantization — the only activation quantization HTP v81's MatMul supports —
clipping heavy-tailed LLM activations. QAIRT 2.43's built-in quantizer
reproduced the same garbage. §4.3 Q5 of that document lists "can W8A8 be made
to work at acceptable quality" as an open question; this effort exists to close
it, one way or the other.

Accordingly the effort has **two acceptable outcomes**, and both are
deliverables:

1. A W8A8 bundle that passes the argmax gate, published to HF.
2. Evidence that v81 cannot do A8 at acceptable quality, published as a report
   and folded into §3.1 / §4.3 Q5.

There is **no device access**. Correctness is established numerically against
the HF reference; every performance number is arithmetic and is labelled as
such.

## 2. Why the payoff is smaller than the name suggests

Weights are **already int8** under W8A16, so A8 changes nothing on the weight
side. Decode on this platform is 100% DDR-bandwidth-bound
(`SA8797P_Deployment_Status_Summary.md` §3.2), so int8 HMX throughput buys
nothing either. The **only** meaningful saving A8 offers is KV-cache traffic.

Arithmetic, for Qwen3-0.6B at CL=1024 (28 layers, 8 KV heads, head_dim 128 —
**re-derive from `config.json` at R0 rather than trusting these**):

```
per token, per layer:  2 (K,V) × 8 kv_heads × 128 head_dim × 2 B (fp16) = 4096 B
× 28 layers                                                            = 112 KiB
× 1024 ctx (full window)                                        ≈ 117 MB
```

Against the ~960 MB/token decode stream (`quantize_aimet.py:172`), that is
**~12% of the stream at full context**, so halving it saves **~6%** — and less
than that on average, since the window is not full for most of a generation.

Two consequences, both load-bearing for this design:

- **The status doc's "~1.5–2× of baseline" estimate for a W8A8 re-test
  (§4.2) is not supported by this arithmetic.** That figure appears to assume a
  compute speedup, which a DDR-bound decode cannot realise. Expect single-digit
  percent, not a multiple.
- **A W8A8 build that leaves the KV cache at FP16 saves approximately
  nothing.** See §4.

## 3. Fixed parameters

| Parameter | Value | Rationale |
|---|---|---|
| Model | **Qwen3-0.6B** | fastest iteration loop; complete gate suite exists; if A8 fails here it fails everywhere |
| Topology | **baseline** — no `--fuse-gate-up`, no `--fuse-qkv`, no `--quant-head` | the only variable versus the shipped W8A16 baseline bundle is activation precision, which is what makes the result attributable |
| Weights | int8 per-channel symmetric (unchanged) | |
| Activations | **int8**, per-tensor asymmetric | the v81 MatMul constraint; not a choice |
| KV cache | **int8** | the only source of DDR saving; see §4 |
| CL / AR | 128 prefill / 1024 ctx | matches the existing baseline bundle |
| Dialog | basic | lade/ladekv are a follow-on, not this effort |
| Gate | `--eval` last-token argmax agreement ≥ 3/4 | the reference in `CLAUDE.md`, benchmarked against a W8A16 control on the same prompts |

**Explicit non-goal:** tok/s. No device.

## 4. The KV decision

`scripts/quant/quantize_aimet.py:179` currently disables the output quantizers
on `k_proj` and `v_proj`, so **the KV cache is FP16 today**. That was
deliberate: it keeps KV out of the cross-graph quantization-parameter problem
entirely.

This design **enables** those quantizers at 8-bit, because per §2 that is where
the entire benefit lives. Doing so reintroduces the constraint recorded at
`docs/NOTES-genie-io.md:177`: KV quant params must be **byte-identical across
prefill, decode, and verify graphs**, and a mismatch is a fatal Genie load
error (the remote error-5005 class). The existing
`--export-decode` / `--adopt-encodings` lineage already enforces this by
construction — the decode graph adopts the prefill run's encodings verbatim
rather than recalibrating.

What changes is that **the enforcement stops being vacuous**. Today no KV
tensor carries an encoding, so nothing can mismatch. Under int8 KV the
invariant becomes real and needs an explicit check (§5.3).

KV is also, independently, a heavy-tailed tensor. It is a plausible primary
cause of A8 failure, and the per-tensor range dump (§5.1) is specified to make
that visible rather than inferred.

## 5. Components

Everything new is opt-in. **With the new flags absent, every existing
invocation of every touched script is byte-identical in behaviour.** This is a
hard requirement: the W8A16 pipeline is the project's only working path and
must not be perturbed.

### 5.1 `scripts/quant/quantize_aimet.py` — new flags

| Flag | Default | Effect |
|---|---|---|
| `--act-bw {8,16}` | `16` | sets `default_output_bw` (currently hardcoded 16 at line 340) |
| `--int8-kv` | off | stops disabling `k_proj`/`v_proj` output quantizers at line 179 |
| `--calib-scheme {tf_enhanced,percentile,mse}` | `tf_enhanced` | range-setting scheme |
| `--percentile FLOAT` | `99.99` | only with `--calib-scheme percentile` |
| `--smoothquant ALPHA` | off | applies §5.2 before quantsim construction |
| `--cle` | off | `aimet_torch.cross_layer_equalization` |
| `--amp-a16 SPEC` | off | promote tensors back to 16-bit. `SPEC` is either a comma-separated list of module-name suffixes (e.g. `k_proj,v_proj`) or `worst:N`, which ranks modules by quantsim-vs-FP32 output MSE on the calibration set and promotes the top N |

`--eval` gains a failure path: when agreement is below the gate, dump
per-tensor activation min/max/percentile ranges and the index of the first
layer whose logits diverge from FP32. **The point is to learn *where* A8 breaks,
not merely that it did** — that dump is the substance of the negative-result
deliverable if the ladder fails.

### 5.2 `scripts/quant/smoothquant.py` — new module

AIMET 2.36 in the `qwen3-deploy` env provides AdaRound, CLE, BN-fold, SeqMSE,
and `mixed_precision`; it does **not** provide `auto_quant` or
`bias_correction` (probed 2026-08-12). Critically, AdaRound and SeqMSE are
*weight-side* techniques and the documented failure is an *activation-range*
problem. The technique that targets it directly — SmoothQuant — is not in AIMET
and is hand-rolled here.

Interface: one function taking the FP model plus `CALIB_PROMPTS` and an α,
mutating weights in place. Applies to RMSNorm→Linear pairs only:
`input_layernorm` → {`q_proj`,`k_proj`,`v_proj`} and `post_attention_layernorm`
→ {`gate_proj`,`up_proj`}.

```
s = max|X|^α / max|W|^(1−α)     (per input channel)
RMSNorm.weight /= s
Linear.weight  *= s
```

Runs on the FP model **before** `QuantizationSimModel` is constructed, so
quantsim calibrates against the smoothed activations.

**Self-check, required:** the fold is mathematically neutral in FP. The module
asserts FP32 logits before and after the fold agree to tolerance on the eval
prompts. A fold that changes FP32 output is a bug in the fold, and without this
assert it would be indistinguishable from a quantization result.

### 5.3 `scripts/validate/check_kv_encodings.py` — new gate

Takes N encodings JSONs — every graph the build produced — and asserts that
every same-named KV tensor carries **byte-identical** quantization parameters
across all of them. Exit non-zero on any mismatch, naming the tensors. For this
effort that is prefill + decode; a later lade build would add the verify graph
to the same invocation.

Guards `docs/NOTES-genie-io.md:177`. Vacuous under W8A16 (no KV encodings
exist); load-bearing under int8 KV. Must be mutation-tested — perturb one
scale, confirm the check fails — since a gate that cannot fail is not a gate.

## 6. The ladder

Inner loop is `quantize_aimet.py --eval` alone. **Nothing touches ONNX, the
converter, or a ctx-bin until the torch gate is green.** The AIMET config in
use (`htp_quantsim_config_v81_per_channel_linear.json`, `hw_version: V81`,
symmetric params, asymmetric activations) reproduces the v81 activation
constraint faithfully, so the failure mode under investigation is visible at
torch level at a cost of minutes.

| Rung | Recipe | Cost | Note |
|---|---|---|---|
| **C** | W8A16 control, same prompts | ~10 min | establishes the number the gate is measured against |
| **R0** | naive W8A8 + int8 KV | ~10 min | **expected to fail** |
| **R1** | `--calib-scheme percentile` (99.9, 99.99), then `mse` | ~10 min each | for A8 LLMs this alone is often most of the fix |
| **R2** | `--smoothquant` α ∈ {0.5, 0.75, 0.85} | ~40 lines once, then free | highest expected value |
| **R3** | `--cle` + `--seq-mse` | cheap | **may be cut** — see §8 |
| **R4** | `--amp-a16` — promote worst offenders to 16-bit, **report the count** | sweep | fallback |

Stop at the first rung that clears the gate. Rungs compose: a passing R2 recipe
carries R1's winning calibration scheme.

**R0 is the mutation test for the gate itself.** It is expected to fail; if it
passes, the conclusion is that the gate is broken, not that W8A8 works. Do not
proceed past a passing R0 without diagnosing the gate.

**AdaRound is excluded.** It is expensive (per-layer optimisation) and it is
weight-side medicine for an activation-side disease. Revisit only if a rung
lands marginally short.

R4 is a fallback, not a stealth success: if it carries the result, the artifact
is **mostly-A8, not W8A8**, and must be named and described as such everywhere
— filename, README, report. The count of promoted tensors is the headline
number, because it quantifies how far v81 actually is from A8.

## 7. Promotion path

Only once the torch gate is green:

1. `full_build.sh qwen3-0.6b-w8a8 128 1024 --act-bw 8 --int8-kv <winning flags>`
   (extra flags pass through to `quantize_aimet.py` per `CLAUDE.md`)
2. `parity_qualla_read.py` and `parity_ladekv_read.py` — topology/read-pattern
   guards. These run **FP32 ONNX**, so W8A8 should not move them; running them
   anyway catches export regressions introduced by the new flags.
3. `check_kv_encodings.py` (§5.3) across the prefill/decode DLC encodings
4. ctx-bin build
5. `bundle.sh qwen3_06b_w8a8 <ctxbin> configs/genie_dialog_qwen3_0.6b.json`

Note the division of labour: the **quantization-quality** gate is `--eval` on
quantsim; the `parity_*` scripts are **topology** gates and cannot see
quantization error. Neither substitutes for the other.

## 8. Risks

| Risk | Handling |
|---|---|
| **Most likely outcome is R0–R1 fail and SmoothQuant carries it.** Plausible that nothing fully clears the gate. | §9 failure exit; R4 bounds the downside |
| **CLE is designed for conv/BN networks.** On an RMSNorm transformer it may be a no-op or actively harmful. | R3 is cut if R2's numbers suggest it is noise. Not a blocker either way |
| **int8 KV across three graphs** — new structural risk, fatal at Genie load time if violated | `check_kv_encodings.py`, mutation-tested, run before any ctx-bin ships |
| **HTP kernel numerics cannot be simulated locally** (`docs/NOTES-genie-io.md`) | quantsim is a faithful proxy for *range clipping*, which is the documented failure mode — but it is not a proxy for kernel-level behaviour. A green local gate is necessary, not sufficient. State this in the README |
| **No device** | every bandwidth figure published is labelled as unmeasured arithmetic |
| **HF hub rate limit: 128 repo commits/hour** | upload via one `upload_folder()` call; if it stalls with blobs pre-uploaded, diagnose per `docs/LOCAL_ENV.md` |

## 9. Failure exit

If C→R4 all fail the gate: **ship no bundle.** Create no HF repo.

Deliver instead:

- `reports/qwen3-0.6b-w8a8-ladder.md` — every rung, its recipe, its argmax
  score, and the per-tensor activation-range evidence from §5.1
- updates to `SA8797P_Deployment_Status_Summary.md` §3.1 (the W8A8 row gains
  the local per-tensor evidence) and §4.3 Q5 (marked answered)

This is a real outcome. The control run at rung C and the mutation test at R0
are what make it credible rather than an unexplained failure, which is why they
are in the ladder rather than skipped as overhead.

## 10. Publication

**New repo: `vinccniv/sa8797p-qwen3-w8a8-bundles`, public and ungated.**

Separate from `sa8797p-qwen3-w8a16-bundles` because that repo's name would
misdescribe a W8A8 artifact. Public matches the stated intent for the
Qwen3-text bundles.

Upload with `HfApi().upload_folder()`, **not** `hf upload-large-folder`. The
CLI resets repo visibility to its own default and silently overwrites the
README (`docs/LOCAL_ENV.md`; observed on this account 2026-08-11). After
upload, verify `HfApi().repo_info(repo).private is False` and report the
observed value rather than assuming it.

README must carry:

- measured `--eval` argmax agreement, and the W8A16 control number beside it
- which mitigation carried the result (and, if R4, the count of tensors
  promoted to 16-bit, with the artifact named mostly-A8)
- the DDR estimate from §2, explicitly labelled unmeasured arithmetic, with the
  note that no device validation has been performed
- the same Qualcomm third-party-component notice as the existing bundles repo —
  the tarballs redistribute QAIRT 2.48.40 runtime binaries that the
  `apache-2.0` tag does not cover

## 11. Out of scope

- lade / ladekv 3-graph variants (follow-on once a basic W8A8 bundle exists)
- fused topologies (`--fuse-gate-up`, `--fuse-qkv`, `--quant-head`)
- 1.7B and the Qwen3-VL-4B text tower
- any change to the W8A16 path
- AdaRound (§6)
