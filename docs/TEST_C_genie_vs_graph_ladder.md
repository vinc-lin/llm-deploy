# Test C — Genie vs. the graph: a prompt-length ladder

**~5 minutes on device. No rebuild, no new ctx-bin, no host toolchain.**
Standalone: everything needed is in `testc_prompts/` beside this file.

---

## 1. Why this test exists

Test B established that the Qwen3-VL-4B text ctx-bins are **numerically correct**
— both shards, decode and prefill, the shard hand-off, rope and cross-token
attention all reproduce the host model. Yet the same bins produce garbage when
driven by Genie.

That narrows the fault to how Genie *drives* the graphs. But it does not narrow
it much, because **Test B bypassed most of what Genie does.** The probe supplies

* `attention_mask`
* `position_ids_cos` / `position_ids_sin`
* a zero KV cache

**from the host**. Genie generates all of those itself. So Test B validated the
graphs *given correct inputs* and says nothing about Genie's mask construction,
its rope/MRoPE table generation, its prompt chunking, or its KV accumulation.

Test C closes that gap the cheapest way available: run **Genie** on prompts whose
correct next token is already known from the source model, starting at one token
and growing. It needs no instrumentation, because the answer is the output.

### What is already ruled out

The 0.6B `UFIXED_POINT_16` probe produced coherent output at **127, 128 and 129**
tokens. 129 spans a chunk boundary. So for a single-shard, 28-layer, plain-rope
model, Genie's chunking, mask construction, KV accumulation and rope are **known
good**. The structural differences left for the 4B are:

1. **MRoPE** (`rope-scaling: qwen3vl-mrope`, sections `[24,20,20]`) — config-driven,
   unique to the 4B, and generated by Genie. Never exercised by any passing test.
2. **The 2-shard split** — the 0.6B is a single ctx-bin.

A rope/MRoPE fault has a signature: it is *harmless at position 0* (cos = 1,
sin = 0, so rope is the identity) and grows with position. A ladder finds it.

---

## 2. Run it

```sh
adb push testc_prompts /data/local/tmp/testc
adb shell
cd /data/local/tmp/v5 && export LD_LIBRARY_PATH=.

for n in 1 4 16 64 127 128 129; do
  echo "===== n=$n ====="
  ./genie-t2t-run -c genie_dialog_qwen3vl_4b.json \
      -p "$(cat /data/local/tmp/testc/prompt_$n.txt)" \
      --max-num-tokens 4
done 2>&1 | tee /data/local/tmp/testc.log
```

`--max-num-tokens 4` keeps each run to a second or two. **Only the FIRST
generated token is the measurement**; the rest is context.

> These prompts contain no chat template and no BOS, matching
> `bos-token: -1` and the absence of `prompt.tags` in the dialog config. Do not
> wrap them. Pass them exactly as the files contain them.

`testc_prompts/expected.json` carries the full top-5 with logits for every rung.

### Read the gap column before drawing any conclusion

The **top1−top2 gap** is how far the winning token leads the runner-up, in
logits. Rungs at **n = 4 and n = 64 are genuinely close calls** (0.19 and 0.46):
ordinary W8A16 quantization noise can flip those, and a mismatch there is **not**
evidence of a defect on its own. The rungs at 1, 16, 127, 128 and 129 lead by
1.5–12.9 logits; a mismatch on any of those cannot be quantization.

This distinction exists because the previous session read a single-token argmax
flip as a defect when the promoted token was 2.81 logits down — plausible only
if the gap is known. Now it is.

### Cross-check

`n=1` and `n=4` were also produced independently by the Test B probe kit
(`decode1tok` → 374, `prefill4tok` last row → 315). Two separate paths agree, so
the reference itself is not in question.

## 4. What each outcome means

| Result | Meaning | Next |
|---|---|---|
| **n=1 wrong** | Genie mis-stages the embedding for a single token, on a graph proven to answer 374 for exactly that input. Rope cannot be involved — at position 0 it is the identity | The fault is in Genie's embedding staging / LUT path. Compare `embedding.size`, `context.n-embd`, and the LUT stride; no rebuild needed |
| **n=1 right, breaks at 16** | Genie is fine at one token but wrong once positions advance and tokens attend to each other | **rope/MRoPE or mask.** The prime suspect: `rope-scaling` is the only Genie-generated input the 0.6B never exercises |
| **right through 127, breaks at 128 or 129** | a chunk-boundary effect specific to the 4B | chunking/KV under a 2-shard model — the 0.6B cleared this for a single shard |
| **all seven right** | Genie drives the 4B correctly for prompts up to 129 tokens | the fault needs length (the failing prompt is 273 tokens) or images. Extend the ladder: 160, 200, 256, 273 |
| **all seven wrong, including n=1** | something global — config, tokenizer, or the wrong ctx-bin loaded | check `MANIFEST.md` md5s first |

A mismatch **only** at n=4 and/or n=64, with 1/16/127/128/129 correct, means
**everything passed** — those two are the tight ones. Report it, do not chase it.

---

## 5. What to send back

1. `testc.log`, complete.
2. For each rung, the **first generated token** verbatim — the exact characters,
   including whitespace. `' is'` and `'is'` are different answers.
3. Any rung that failed to load, with `adb logcat -d`.

If the run is quick, repeat the first failing rung two or three times: a result
that changes between identical runs is a different problem from one that does
not, and that distinction is free to collect here.

---

## 6. Why this is worth doing before anything else

Every remaining hypothesis — MRoPE, mask construction, chunking, KV, the split —
predicts a *different* rung as the first failure. One five-minute run orders them,
and it does so without a rebuild, without instrumentation Genie does not expose,
and without another host round-trip.

It also cannot be invalidated the way Test 5 of the 2026-08-15 session was: there
is no probe kit, no hand-built input encoding, and nothing to fall out of sync
with the ctx-bin. Genie reads the prompt, and the model either predicts the right
token or it does not.
